# Northpoint frontend

## Role workspaces

Northpoint serves HTML, CSS and native JavaScript modules directly from `frontend/`. The four role entry points are `/hr/index.html`, `/supervisor/index.html`, `/c_manager/index.html`, and `/employee/index.html`. Nginx can send users directly to their assigned folder. When the server serves the root landing page, it reads `/auth/me` and opens the matching role folder. The role entry checks the same session before making data requests. Shared assets are under `frontend/css/` and `frontend/scripts/`. The old `/northpoint/` landing URL still routes signed-in users to their assigned workspace.

[RBAC_MATRIX.md](RBAC_MATRIX.md) defines permissions. HR retains the existing layout and its allowed workflows. Staff can find employees to view or issue violations as permitted. The Concerned Employee workspace opens only the signed-in employee’s violation history. It has no directory or global search.

### Backend requirements for rollout

- Return an authoritative `role` from `GET /auth/me` with one of `hr`, `supervisor`, `c_manager`, or `employee`. For a Concerned Employee, include `employee_id` linked server-side to the session. The current backend returns name fields but omits role and employee linkage. An unrecognized or missing role blocks the workspace. An employee with no linkage sees a dedicated message and the frontend requests no records.
- Enforce the matrix on the server before deploying to restricted accounts. Derive access and identity from the authenticated session on each protected route. In particular, enforce ownership on `GET /app1/employees/{id}/violation-history` and deny alternative routes that could expose other employees’ records. Apply role checks to photo files and metadata, including GPS fields and any location metadata embedded in images.
- The current browser `POST /app2/upload` rejects uploads. The Android `POST /app2/mobile-upload` uses tracker authentication. Provide a session-authenticated Supervisor proof upload contract. Until then the Supervisor workspace explains that browser uploads are unavailable.

## Company rulebook data

The importer reads the private `COMPANY_RULES.md` outside `frontend/` and constructs its data in memory. No Markdown, HTML or JSON copy of the document is published by the website or generated by the website build. The document defines 8 company categories, 78 specific violations and 173 penalty tiers. It has 77 sections; VIII.F becomes two selectable rules because it defines two different loss-amount bands. The backend retains source notes for maintenance; the website shows violation names and penalties without document links or provenance text.

The website continues to read live backend data. Building or opening the website does **not** seed or replace records automatically. To populate a server, set `NORTHPOINT_USERNAME` and `NORTHPOINT_PASSWORD` for an existing browser account, then run these from this folder:

```powershell
node tools/import-company-rules.mjs --base-url http://localhost:8081/app1/
node tools/import-company-rules.mjs --base-url http://localhost:8081/app1/ --apply
```

The first command previews changes. The second saves a rulebook backup in the operating system's temporary `northpoint-rulebook-backups` folder, then imports through authenticated APIs and verifies every rule. Use `--backup-dir <folder>` to choose a private backup location and `--rules-file <path>` when the private source is elsewhere. Re-running skips matching data and does not duplicate entries. Existing inactive states, unrelated categories, employee records and issued penalty snapshots are preserved. Existing notes are retained alongside source notes. Importing does not add automatic enforcement of policy conditions.

## Current offense-based integration

Open http://localhost:8081/ and sign in. The earlier API showcase is available at /showcase.html on the local frontend mount.

Categories come from /violation-types; each specific violation is a /subsections record with its own penalty tiers. Issue Violation uses Employee → Category → Specific violation → Review → Confirm. Preview reads the employee offense summary and current penalty schedule. Confirmation rechecks both; the backend assigns the final number and stores the penalty snapshot. The frontend sends subsection_id, notes and issued_by; it never posts points, strikes, an offense override or an employment-status change.

Removed violations remain part of total offenses and repeat-offense history. Active Violations excludes removals. Watchlist means a 3rd or later offense on a specific violation, including removed records. Removal sends the signed-in actor through X-Actor and only reason in the body. Blank optional reasons are explicitly recorded as “No reason provided.” to satisfy the current API.

Violation Types opens a category’s specific violations and a full-page editor for wording and penalty tiers. Updating tiers does not rewrite issued penalty snapshots. Delete category requires a separate confirmation showing the current number of specific violations. It uses the backend's single category-delete request, which cascades to its specific violations and penalties and rejects categories still in use. A changed child list requires the user to review the count again before deletion.

Employees and violations retain 8-row pages, compact horizontally scrollable mobile tables, the accessible employee picker and the current Northpoint design. Profiles, history, reports and today indicators use offense counts instead of points/strikes. No records are persisted or queued for saving in browser storage; failed requests show errors.

Employee profiles show Active Violations and Violation History tabs. The active tab displays the latest unremoved record for each specific violation; this is a presentation change and does not rewrite earlier records. History includes all issued records and removal snapshots, including reused backend record IDs, with six rows per page. Removal confirmation is pre-checked when opened from the profile's active tab. Watchlist starts at the third offense on a specific violation, including removed history, consistently across dashboard, employee filters, reports and Help.

Today indicators reconstruct the Manila-midnight baseline by matching employee, rule, offense number and timestamps. They do not assume that a violation ID is unique across active records and removal history: SQLite can reuse IDs after removal. Unrelated metrics remain available if a particular audit detail cannot be reconstructed. Visible page-heading blocks are removed; page names remain in the top bar and accessible headings, and page action buttons remain available.

Source edits are served directly. The FE version remains v.FE-0.3a.

## Photo Library and sign-in

HR can browse proof photos, view original downloads and open Photo Activity. Supervisors can browse proof photos. The workspace limits location and path views to HR. The separate Camera bookmark redirects to the Photo Library for roles that can open it.

The signed-in account comes from the existing read-only `/auth/me` endpoint. It uses the HTTP-only session cookie and returns the user ID, username and profile names; Northpoint displays `full_name`, using available first/last names or the username when profile names are missing. Successful responses are marked no-store, and missing/expired sessions return 401. Settings shows the signed-in name as read-only. Existing Nginx `/auth/` routing supports both session checks and logout; no backend change is needed for the frontend Sign Out button.

To sign out, open the profile button at the top right and choose **Sign Out**. Northpoint navigates to the existing `/auth/logout` endpoint, which deletes the current session, clears its cookie, and redirects to sign-in. The action waits for any active save to finish. Pages restored through Back are reloaded through Nginx so a logged-out session cannot keep using a restored dashboard.

## Yesterday comparisons

Dashboard Employees, Total Violations, Total Points and Watchlist show signed numeric changes against the prior day’s closing totals. Reports Daily Average compares the selected rolling window with the same-length window ending yesterday. Manila time defines day boundaries. No percentage or prior-period label is used. Photo Total Photos and Storage Used have no comparison indicators.

Comparisons reverse today’s recorded HR audit events. New hard-delete events include aggregate and violation snapshots so totals can be reconstructed later. Old hard-deletion logs without these snapshots, missing history, and department transfers without prior department details show `— vs yesterday` rather than fabricated changes. Hover the indicator for the reason. Restart `app1` after updating `queries.py`; no schema migration is required.

Northpoint uses the backend API for employees, violations, rulebook, dashboard, reports, History and Calendar. The existing desktop/phone design remains unchanged. Records are never stored in the browser or queued offline, and failed requests never fall back to sample data.

## One API configuration

By default **frontend/scripts/config.js** uses the same server address as the page:

```javascript
const BASE_URL = '';
```

This makes both `http://localhost:8081/` and a tunnel address use their own `/app1/`, `/app2/`, and `/auth/` endpoints. Serve the whole frontend directory so `/scripts/config.js` is available. You may set an absolute API URL for a special deployment, but the browser needs an appropriate same-origin authentication and CORS setup. Save and reload after any configuration edit; no rebuild is needed. The older frontend/js/script.js configuration does not control Northpoint.

For a phone, localhost refers to the phone. Open the tunnel address or `http://YOUR-PC-LAN-IP:8081/` from the phone and sign in there; the API follows that address automatically.

## Run with the local backend

Start Docker Desktop. In the **repository root**, run:

```powershell
docker compose -f docker-compose.yaml -f docker-compose.local.yaml up -d --build
```

Open **http://localhost:8081/**. The existing backend sign-in page appears when there is no valid local session; after signing in, Northpoint opens at `/`. A valid session with a recognized role opens its assigned workspace. API requests use the same-origin session cookie; an expired session redirects to sign-in, while connection errors stay visible for retry. Opening index.html directly or using a separate preview port does not provide this same-origin login session.

If you need an account, the backend's existing account command is:

```powershell
docker compose -f docker-compose.yaml -f docker-compose.local.yaml exec auth uv run --no-sync python -m auth.manage create-user YOUR_USERNAME
```

If the stack is already running, apply the frontend mount by recreating only Nginx:

```powershell
docker compose -f docker-compose.yaml -f docker-compose.local.yaml up -d --no-deps --force-recreate nginx
```

The local Compose overlay already mounts `frontend/`. The checked-in Nginx configuration currently authenticates the static site but has no role-specific folder locations. To provide server-side folder isolation, the deployment must use its role-aware Nginx configuration and serve the whole `frontend/` tree. The checked-in production Dockerfile copies only `frontend/northpoint/`, so an image built with that copy instruction does not include the new role folders or shared paths. API authorization remains the responsibility of the backend.

Your signed-in full name is used automatically for changes. Existing documented X-Actor and removal payload behavior is retained; Nginx also forwards the authenticated name. Loading, success, conflict, access and lost-response handling remain in place; unconfirmed saves are checked by GET before another write is allowed.

## Running the frontend

Use the same origin for the HTML pages and `/auth/` so the existing session cookie is available. `node serve.mjs` is an optional static file server for checking paths and assets. Open the Docker-hosted site for authenticated API access.

## Photo Activity and API routes

Photo Activity now fetches eight events per page from `/app2/activity`. Search, team member, action, and selected-date filters are sent to the server. “All dates” removes the feed's date restriction; the adjacent calendar always summarizes the displayed month using `/app2/activity/digest?include_items=false`. Calendar shading uses the returned daily totals and the text below it uses the server's summary. No full activity-history download occurs when opening the photo library.

The “Changed by” options come from `/app2/activity/actors`. Clicking a photo name in Activity or “View History” in Photo Details opens its paginated `/app2/photos/{id}/history`, including retained history for deleted photos. “Photos on this page” uses the read-only `POST /app2/photos/batch` with `{ "ids": [...] }`; it shows only photos linked to that event page and explicitly reports missing/deleted photos. It does not upload or modify records.

Activity requests cancel and ignore superseded reads. Errors clear the results and show a retry button. Page navigation reuses the latest successful monthly summary and actor options in memory; reopening Activity or retrying refreshes them. Nothing is persisted in browser storage.

The public URL adds the service prefix: schema `/activity/actors` in app2 becomes `/app2/activity/actors`. The existing `config.js` remains the server configuration. The browser must use the same server as the signed-in session.

Photo Activity → Photos on this page: select a thumbnail or photo name to open the enlarged viewer. Back to photos restores the same gallery. Image loading failures show a retry option. The viewer adapts to desktop and phone screens.

The account name comes from `/auth/me`: `full_name`, then available first/last names, then username for older accounts without profile names. New issued-by and removal payloads use this name. Historical names for other accounts stay as returned by the backend; `/auth/me` only identifies the current account.

## Source folders

From `frontend/`, edit the role entries in their folders, common startup and permissions in `scripts/shared/`, and application features in `scripts/northpoint/`. The API configuration is `scripts/config.js`.

- `app.js`: shared workspace shell, screen routing and action dispatch.
- `api/`: shared API transport, allowed routes and request helpers.
- `auth/`: signed-in account and session handling.
- `state/`: shared application data, backend loading and mutations.
- `features/dashboard/`: dashboard view.
- `features/employees/`: employee requests, forms, picker and New labels.
- `features/records/`: employee, violation and violation-type list views.
- `features/history/`: calendar, daily summaries and history API contracts.
- `features/reports/`: reports, analytics and yesterday comparisons.
- `features/photos/`: photo library, downloads, activity, viewer and API handling.
- `features/settings/`: settings, help and secondary page routing.
- `shared/`: reusable domain helpers, loading states, filters and mobile behavior.
- `styles/`: shared, photo and compact-table styles.
- `assets/`: company logo and bundled fonts.
- `preview/`: retained preview helpers, excluded from the live website build.

Account controls: the top-right account name opens a Sign out dropdown. Settings also offers Sign out and the text-size preference. Users & Roles and local role/department workspace views have been removed; backend authentication remains unchanged.

Photo Library, Photo Activity, History and report periods use the same compact dropdown filter components as the record lists.

Violation removal reasons are optional in the form. The backend currently requires a non-empty reason, so a blank field sends the explicit text `No reason provided.`. Existing removal confirmation and error handling remain in place.

## Sign-in page

The existing centered sign-in UI is available at `login.html`. It uses the supplied Northpoint wordmark and username/password fields.

The form submits the existing backend fields `username`, `password` and `next` via a normal POST to `/auth/login` on the page's server. The backend continues to create the HttpOnly session cookie and return the success redirect. The frontend stores no credentials. A Show/Hide password button, required-field validation, duplicate-submit guard and optional sign-in error messages are included.

The existing backend still renders `GET /auth/login`, and the existing static Nginx location requires authentication. Creating this frontend page alone does not replace that route or make it public. For backend adoption, `deployment/signin-nginx.example.conf` shows the public page location, GET routing, unchanged POST forwarding, and invalid-credential/rate-limit error redirects. It is a reference only, not automatically installed. No backend, Nginx or Docker files outside frontend were changed.

While signed in, preview the page at `http://localhost:8081/login.html`. For a UI-only local preview, `node serve.mjs` also serves `/login.html`; actual sign-in must use the server hosting `/auth/login`. Error messages can be previewed with `?error=credentials`, `?error=rate_limited` or `?error=session`. The `next` value is restricted to local absolute paths; invalid redirect targets fall back to `/`.

## Map Tracking (app3)

Open Map Tracking in the main navigation or use `/#tracking` while signed in. The page uses the existing app3 services: `GET /app3/devices?include_offline=true`, `GET /app3/live/{device_id}` and `GET /app3/route/{device_id}`. The service address follows the existing `config.js` server automatically, including localhost and ngrok. No separate tracking server URL is configured in the frontend.

Select a device from the list to show its current/last reported location, accuracy and today’s segmented route. Fit route shows the available route; Keep device centered follows incoming locations. The shared compact toolbar searches tracker names/device IDs and filters online/offline devices. An exact ID can also be looked up from an empty search result. Backend failures and invalid responses are shown as errors; no sample devices or locations are inserted. The initial map view uses the same Cagayan de Oro area as app3’s original map and is not a device position.

Device and selected-location reads update every five seconds while the page is open and visible; selected route reads update every fifteen seconds. Refresh also reloads the route. Requests stop when leaving the page or hiding it, and aborted/outdated replies cannot replace a newer selection. Tracking starts and stops in the phone app, not from this management page. The backend considers a device online when it reported within fifteen seconds; its live device list is held in backend memory. An empty list means no devices are currently known to the running tracking service.

The frontend bundles Leaflet 1.9.4 locally with its BSD license under `frontend/scripts/northpoint/vendor/leaflet/`. JavaScript and CSS integrity hashes match the official Leaflet distribution. OpenStreetMap tiles load over HTTPS with visible map attribution and normal browser caching. Internet access is needed for base-map tiles. The original backend map, GPS upload flow, authentication, Docker and Nginx files were not changed.

Source: `frontend/scripts/northpoint/features/tracking/` and `frontend/css/northpoint/map-tracking.css`. The frontend version remains `v.FE-0.3a`.

On phones, Map Tracking places the map immediately under the compact page title. Refresh, search/filter controls, device summary and the device list follow below. Desktop retains the existing toolbar and side-by-side device/map panels. The responsive helper moves the existing controls without duplicating the map or starting another polling loop.
